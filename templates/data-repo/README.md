# Mission Control data

The plans and roadmaps of one Organization, read and written by its Mission
Control App through [repository-db](https://github.com/Lazurio/repository-db).
This repository is checked out on branch `v3` as the `db/` directory of the
Mission Control Module.

| Path | Holds |
| --- | --- |
| `data/mission-control/mission-control.config.json` | the Organization's settings, e.g. the plan prefix |
| `data/mission-control/plans/<year>/<month>/<CODE>-<slug>.yaml` | one plan per file |
| `data/mission-control/roadmaps/<year>/<CODE>-<slug>.yaml` | one roadmap per file |
| `scripts/validate.ts` | the validator repository-db runs before every publish and CI runs on every pull request |
| `scripts/mission-control-check.js` | Mission Control's own check of the data (schemas, rules across records, evidence files, the frozen history, YAML parser), generated by Mission Control; never edited here |
| `schemas/*.schema.json` | JSON Schemas of one file, generated by Mission Control for editors and tools; never edited here |
| `data/mission-control/history.lock.json` | only in a repository that Mission Control 3.x used: its history (ledgers, changesets, import reviews, reports) frozen by digest; written by `bun scripts/validate.ts --freeze-history`, never by hand |

A change is published from the Mission Control App (Draft & Publish) or as a
pull request to `v3`. Validate locally with `bun scripts/validate.ts`: it
passes exactly when the Mission Control App accepts the records. The CI job
`validate` runs the same command and is the required check of `v3`.

Mission Control 4 adds nothing beside the records: any file under
`data/mission-control/` other than the settings, the plans, the roadmaps and
the frozen history fails the check, and so does any change of the frozen
history. Changing the history on purpose is a new freeze, reviewed as a
change of `history.lock.json` in its pull request.
